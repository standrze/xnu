## Property-padding compatibility finding

After the third recovery, metadata-only reads of `/sys/firmware/fdt` reproduced
a structure rejection in the current Linux boot: nonzero property padding at
offset 113, after three tokens (total 80360, structure size 72532). The checker
used seeks to skip every property value, including seeds, and printed only
numeric metadata and a reason. This is a different firmware-produced tree from
the standalone run, so the exact standalone cause still needs confirmation.

The native and Python parsers now ignore the contents of property alignment
padding, retaining its bounds and alignment checks. Node padding, token order,
property lengths and all memory/reservation semantics are unchanged. This is
an explicit compatibility allowance: DTSpec chapter 5 specifies zero padding.
Tests use nonzero padding for lengths 1, 2 and 3, verify returned values exclude
padding, and reject truncated buffers. No real property contents are fixtures.

Upstream explanation found after the run: Raspberry Pi's official
[2712 release notes](https://github.com/raspberrypi/rpi-eeprom/blob/master/firmware-2712/release-notes.md)
list a 2026-06-17 change making images without ARM64 headers honor an explicit
`kernel_address`, avoiding relocation. The tested EEPROM is 2026-05-26 and
predates that fix. This is strong evidence for the observed raw-image behavior;
the precise firmware implementation is not public in this checkout. Next
evaluate and pin a release containing that fix instead of assuming that another
config-only retry on May 26 will behave differently. Keep the placement guard
regardless. No newer EEPROM has been installed as part of this investigation.

## Observed sequence

- Firmware read the SD config, DTB, BL31 and 16,290,872-byte probe image.
- It loaded the probe at the configured `0x6000000`, then explicitly reported
  `Kernel relocated to 0x80000`. FDT was reported at `0x8000000`, size `0x13a1a`.
- TF-A identified itself as `v2.10.0(debug):332b62e`, initialized GICv2 and
  reported its normal-world entry address as `0x80000`.
- The probe printed UART registers, EL2 entry and subsequent EL1 state.
  Primary MIDR was `0x414fd0b1`, MPIDR `0x81000000`, CNTFRQ `0x337f980`.
  EL1 CurrentEL was 4, SCTLR `0x30d00800`, DAIF `0x3c0`.
- The probe printed primary feature registers, then
  `RPI5XNU:BL33:FDT MEMORY_CPU_OR_PSCI_CONTRACT_REJECTED`.

No secondary, timer IRQ, entropy, materialization or XNU execution is proved.
The exact FDT rejection branch is not distinguished by the current early
diagnostic; do not attribute it to a particular property without evidence.
Relocation is independently observed and violates the intended linked-placement
contract. Some PC-relative code executing successfully does not establish that
all absolute pointers or writable allocations remain valid after relocation.

Next: restore Linux by powering off and removing the test SD before restarting,
then investigate firmware image-header/relocation behavior and add a pre-write
linked-placement guard. Do not retry the same image unchanged or assume that
`kernel_address` alone fixes the final execution address. The missing cmdline
file warning is also recorded, but firmware continued into BL31 despite it.
